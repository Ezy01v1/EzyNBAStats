## Phase 0: environment + data layer (2026-11-03)

- **What I built:** a single `NbaClient` (`src/sportslab/data/client.py`) that every `nba_api` call must go through: disk cache in Parquet, >=1 s between real requests, 60 s timeout, retries with exponential backoff.
- **Why one gateway:** stats.nba.com throttles bursts and blocks many cloud IPs. Centralizing the rules means no module can accidentally hammer it, and a finished season is downloaded exactly once.
- **Cache design:** key = endpoint name + sorted params (param order does not matter). Cache hits skip the rate limit. Writes go to a temp dir and are renamed, so a crash never leaves a half-written entry. `max_age` lets recent-data modules (daily dashboard) expire entries; finished seasons never expire.
- **Testing without network:** time (`sleep`, `clock`) and the endpoint are injected, so rate-limit and backoff behavior is tested deterministically in milliseconds. One separate `-m network` smoke test hits the real API (`LeagueGameLog` 2023-24: 2460 team-game rows = 1230 games).
- **What failed:** I set `requires-python >=3.11`, but the latest numpy needs 3.12+. uv caught it at resolve time. Floor is now 3.12. Also `winget` does not exist on this Windows 10 LTSC; uv installed with `pip install --user uv` and runs as `python -m uv`.
- **To improve:** result sets are stored by index (`0.parquet`...); name them if an endpoint with duplicate column names shows up. Add one smoke test per new endpoint as modules need them.

## Module 1, part 1: Elo baseline (2026-11-03)

- **Result:** on the untouched 2025-26 test season the tuned Elo (K=24, home advantage 40, carryover 0.7) scores log loss 0.6037 vs 0.6931 for a coin and 0.6875 for "home team wins at the historical rate". Brier 0.208, favorite wins 68%. Calibration is reasonable; extreme bins have too few games to judge.
- **Hypothesis vs. result:** I had no prior ("mi intuicion es X"), so I compared against baselines. Lesson: a baseline is a hypothesis you can always state, even without intuition.
- **Surprise:** home-court advantage fell from ~59% (to 2018-19) to ~55% since 2019-20 (2022-23 at 58% is an exception). The classic Elo home bonus of ~100 points is outdated; validation preferred 40.
- **What failed:** (1) real data has neutral-site games (both teams marked "@"), which broke my "one home team per game" assumption; now flagged and excluded from scoring. (2) The best home advantage sits at the edge of my grid (40 = lowest tried); I should have included 0 and 20. (3) I saw validation and test output in the same run, so extending the grid now makes 2025-26 a "second look", not a clean test. (4) I wrote "7 consecutive seasons" for the home-rate drop; 2022-23 contradicts it. I caught it by checking the table before shipping the notebook.
- **Tooling lessons:** Windows PowerShell 5.1 `Get-Content`/`Set-Content` silently corrupted UTF-8 accents in a file; fixed with a byte-exact reverse mapping. Iterating pandas Series row by row was 2x slower than plain lists.
- **Still to do for the module:** logistic regression and XGBoost compared against this Elo (they need pre-game features: rest days, recent form, rating difference), margin-of-victory Elo as an exercise, speed up the 280-run tuning grid (first page load ~25-30 s).

## Module 1, part 2: logistic regression and XGBoost (2026-11-03)

- **Result (test 2025-26, 1225 games):** Elo 0.6037 log loss; logistic on Elo difference only 0.6049; logistic with form + rest 0.6002; XGBoost 0.6051. Paired gain over Elo: logistic(all) +0.0035 [-0.0022, +0.0092], XGBoost -0.0014 [-0.0072, +0.0044]. No interval excludes 0 on the test season. On validation logistic(all) was +0.0041 [+0.0002, +0.0079]: same sign, barely significant.
- **Hypothesis vs. result:** again no prior ("sin intuicion, corre"). The useful discipline was reporting the per-game paired difference with an interval: comparing 0.6037 vs 0.6002 as bare averages would have looked like a win and is within noise.
- **What I learned:** the complex model did not earn its complexity. 5 near-linear features + heavy sports noise = trees add variance, not signal. Form (shrunk last-10 margin) was the second most used feature after Elo difference; rest/back-to-back are small and collinear with each other, so their coefficients should not be read individually.
- **Caveats I should not forget:** 3 models x 2 stages compared with no multiple-comparison correction, so a lower bound of +0.0002 means little. Elo parameters were tuned on the validation seasons, which slightly favors Elo there. The Elo feature itself is computed with those tuned parameters.
- **What failed / fixed:** my paired-gain unit test used a constant per-game gain, giving a zero-width interval (test bug, not code bug). `st.bar_chart` stacks series: I had put logistic coefficients and XGBoost importances (different scales) in one chart; split into two.
- **Likely next lever:** information, not models. Injuries, lineups and star rest are absent from every feature here. Exercise 2 in the notebook: add one feature, predict the sign and whether the interval excludes 0, then measure.

## Module 3: player comparator (2026-11-03)

- **Result (2025-26, 279 players with >= 1000 min):** USG% vs TS% Spearman -0.02 [-0.14, +0.10] (no detectable relation); controlling for REB% as a proxy for "big man" it is -0.00. Only 2021-22 excludes 0 (-0.14 [-0.24, -0.03]) and the value drifts towards 0 in later seasons. Net rating vs PIE: +0.27 [+0.15, +0.38], only 6 of 20 players in both top-20 lists.
- **Hypothesis vs. result:** again no prior ("sin intuicion, corre"), so the reference was the null (rho = 0). Lesson: "usage tax" is a popular story that, among rotation players, explains almost none of the efficiency spread. It says nothing about raising one player's usage, which is a causal question this data cannot answer.
- **Data surprise:** `LeagueDashPlayerStats(Advanced, Totals)` returns MIN as minutes PER GAME, not total, while other columns (FGA, POSS) are totals. Caught by looking at the describe() (max 38 min) and confirmed with possessions per minute (~2.1). `clean_player_stats` derives `minutes = MIN * GP` and raises if that ratio ever breaks; the network smoke test covers it.
- **Percentile radar:** percentiles make unit-less axes comparable, but throw away magnitude; the page always shows raw values, games and minutes next to it. Percentile uses mid-rank for ties so the best of N is not "100".
- **What failed:** (1) my first "no association" unit test used random noise; about 1 seed in 20 excludes 0, so it was seed-dependent. Replaced by a symmetric U shape whose Spearman is exactly 0. (2) A first symmetric range was off by one (-75..74 is not symmetric) and gave -0.02.
- **Caveats to remember:** net rating is a team quantity (depends on teammates), so "net rating >> PIE" lists are a hypothesis about role players on good teams, not a finding. PER/BPM are replaced by PIE; if wanted, import a Basketball Reference CSV later. Five seasons are not five independent samples (same players).

## Module 2: shot charts (2026-11-03)

- **Result (hypothesis B, 2025-26, ~219k league shots):** points per shot by zone: restricted area 1.34 > corner 3 1.16 > above-the-break 3 1.05 > paint outside RA 0.89 > mid-range 0.83. Long mid-range (16-24 ft) 0.80 vs 1.05 for a top-of-the-key 3, a gap of ~0.24 that is much larger than sampling noise (Wilson interval of about +-0.02) and holds in all five seasons 2021-22..2025-26. This is what was shot, not what would happen if everyone shot from one zone; free throws are not counted.
- **Hypothesis vs. result:** no prior ("sin intuicion, corre"); reference "all zones are similar" is clearly rejected. Lesson: with ~10,000+ attempts per zone the noise is tiny, so large league-level differences are real; the problems start at the player level.
- **Data surprise:** the league-wide zone table that comes with every `ShotChartDetail` response is identical for every player, so the whole-league question needs 1 request per season, not 500. `team_id=0` returns all of a traded player's shots.
- **Biggest lesson (shrinkage experiment):** predicting a player's second-half zone FG% from the first half, the raw percentage is the WORST predictor, worse than ignoring the player and using the league rate (0.00650 vs 0.00470 weighted MSE); shrinking with k~160 pseudo-attempts cuts the error 40% (0.00393). My initial convention (k=20) was far too weak; the error is flat for k in 80..320, so the project default is now 100. Meaning: with half a season of shots, differences between players inside one zone are mostly noise.
- **Where vs. how:** `selection_vs_making` splits points per shot into the quality of the zones a player shoots from and his conversion relative to the league in the same zones, with a per-shot-residual interval. Example (Jokic 2025-26): -0.03 from where he shoots, +0.18 [+0.11, +0.24] from how he converts; chosen because he leads PIE, so he is a selected extreme case, and zones do not separate open from contested shots.
- **What failed / fixed:** (1) page titles were too long and got cut; added line breaks and moved the legend. (2) A first AppTest indexed the wrong selectbox. (3) The old shrinkage unit tests encoded k=20; rewrote them to state the property (few shots stay near the league, many shots overwhelm the prior). (4) Chained `ruff check && python` meant a lint error silently skipped the experiment run; check exit codes before trusting "no output".
- **Caveats to remember:** shrinkage validated only on 100 high-minute players, one season, one split. Mid-range includes late-clock shots. Not done: open vs contested shots (needs tracking data), positions, free throws.

## Module 4: player roles, clustering (2026-11-03)

- **Result (2025-26, 279 players with >= 1000 min, 16 style features):** silhouette peaks at 0.21 (k=3), above the column-shuffled null (~0.05) but below the usual 0.25 "weak structure" line. Only k=3 is stable: bootstrap ARI 0.87 and 0.76 against 2024-25; from k=4 on, ARI falls to ~0.5 (bootstrap) and 0.32-0.45 (other season). The five classic positions are not recoverable from stats. The first two principal components explain 57% of the variance, and groups touch each other: these are cuts of a continuum.
- **Hypothesis vs. result:** no prior ("sin intuicion, corre"); reference was the null "no structure". Lesson: k-means returns k clusters for ANY data, so a cluster is a claim that needs evidence (null silhouette, stability, other season), and the null only proves variables are correlated, not that there are islands.
- **The three groups (names are mine):** low-usage perimeter role players (125; corner threes, few turnovers, but also some low-usage bigs like Okongwu), high-usage creators and scorers (111), rim-area bigs (43). The creators group lumps very different players: Jokic, Cunningham, Wembanyama, Giannis, Durant and Maxey all land there, and Wembanyama and Giannis are the two most isolated players in the league (nearest-neighbour distance 5.1 and 4.7 vs a median of 2.1).
- **Biggest caveat (feature sensitivity):** the k=3 partition agrees with the full-feature one at ARI 0.43 using only per-100 stats, 0.58 without shot zones, 0.66 with only zones+usage+TS%, and 0.87 without fouls/turnovers. The groups depend on which variables I chose, so "3 roles of the NBA" is not a finding.
- **Data surprises:** in the per-100 table `MIN` is minutes per 100 possessions (~48), not minutes played; real minutes still come from the Advanced table. `PlayerIndex` only returned ~195 players, so no positions to compare against. `LeagueDashPlayerShotLocations` returns two-level columns that become strings in the Parquet cache; the parser handles both forms (tested).
- **What failed / fixed:** (1) my feature-subset test used blobs where two columns carried identical centers, so one subset could not separate the groups (test data bug, not code bug). (2) A permutation-correlation test threshold (>0.5) was a hair above the real 0.499. (3) Browser visual check failed this time (navigation denied); verified only with AppTest and notebook outputs, not by eye.
- **Smoke test earned its keep:** the network test found NaN (not 0) zone attempts for 4 players with a few minutes in 2023-24; none in the >= 1000-minute pool, so results are unaffected, but the loader now reads them as 0 attempts (tested).
- **Not done:** hierarchical or Gaussian mixture clustering (soft membership), decorrelating features before clustering, tracking data (defense, passing), more seasons.
